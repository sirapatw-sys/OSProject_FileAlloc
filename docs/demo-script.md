## 2. บทพูดและลำดับการกดบนหน้าจอ (Step-by-Step Script)

### ช่วงที่ 1: บทนำและเป้าหมายโปรเจกต์ (0:00 – 1:00)

**การกระทำบนหน้าจอ:**
- เปิดหน้าเว็บ `index.html` แบบเต็มจอ (Full Screen)
- ตรวจสอบว่า Used Blocks เป็น 0 และ Free Blocks เป็น 64

**บทพูดผู้พรีเซนต์:**
> *"สวัสดีครับอาจารย์และเพื่อนๆ ทุกคน วันนี้กลุ่มของพวกเราขอแนะนำโปรเจกต์ **FileAlloc** ซึ่งเป็นเครื่องมือจำลองการจัดสรรบล็อกบนดิสก์ของระบบไฟล์ (File System Block Allocation Visualizer)*
>
> *ในวิชา Operating Systems เราเรียนทฤษฎีว่าไฟล์ขนาดต่างๆ ถูกจัดเก็บลงบนบล็อกของดิสก์อย่างไร แต่หลายครั้งเรามองไม่เห็นภาพว่า Contiguous, Linked และ Indexed แตกต่างกันอย่างไร และทำไมบางวิธีถึงเกิดปัญหาพื้นที่ไม่พอทั้งที่ดิสก์ยังว่างอยู่*
>
> *ในระบบจำลองของเรา เราจำลองพื้นที่ดิสก์ขนาด 64 บล็อก โดยมีระบบรักษาความคงสภาพ (System Invariant) ว่าจำนวน **Used Blocks บวกกับ Free Blocks จะต้องเท่ากับ 64 เสมอ** เดี๋ยวเรามาดูการทำงานจริงกันครับ"*

### ช่วงที่ 2: สาธิตการจัดสรรพื้นที่ทั้ง 3 รูปแบบ (1:00 – 2:30)

#### ขั้นตอนที่ 2.1: Contiguous Allocation
**การกระทำบนหน้าจอ:**
1. กรอก File name: `kernel.bin`
2. กรอก Size: `6`
3. เลือก Allocation method: `Contiguous Allocation`
4. กดปุ่ม **Create file**

**บทพูดผู้พรีเซนต์:**
> *"เริ่มจากวิธีแรกครับ **Contiguous Allocation** เราสร้างไฟล์ชื่อ `kernel.bin` ขนาด 6 บล็อก*
> *(ชี้ที่ Disk Grid)* *จะสังเกตเห็นว่าระบบจัดสรรบล็อก 0 ถึง 5 ซึ่งเรียงติดต่อกันเป็นผืนเดียว วิธีนี้มีข้อดีคืออ่านข้อมูลแบบ Sequential และ Direct Access ได้เร็วมาก เพราะหัวอ่านไม่ต้องข้ามไปข้ามมาครับ"*

#### ขั้นตอนที่ 2.2: Linked Allocation
**การกระทำบนหน้าจอ:**
1. กรอก File name: `music.mp3`
2. กรอก Size: `5`
3. เลือก Allocation method: `Linked Allocation`
4. กดปุ่ม **Create file**
5. เลื่อนเมาส์ชี้ดูการ์ดไฟล์และสายโซ่บล็อก

**บทพูดผู้พรีเซนต์:**
> *"วิธีที่สองคือ **Linked Allocation** เราสร้าง `music.mp3` ขนาด 5 บล็อก*
> *(ชี้ที่ Disk Grid)* *สังเกตว่าบล็อกไม่ได้เรียงติดกันแล้ว แต่ถูกสุ่มวางในบล็อกที่ว่าง และหากดูที่การ์ดไฟล์ด้านล่าง จะเห็นสายโซ่พอยน์เตอร์ เช่น บล็อก A ชี้ไป B ชี้ไป C และตัวสุดท้ายจะชี้ไปที่ `null` เสมอ ทำให้ไม่จำเป็นต้องใช้บล็อกที่ติดกันเลยครับ"*

#### ขั้นตอนที่ 2.3: Indexed Allocation
**การกระทำบนหน้าจอ:**
1. กรอก File name: `database.db`
2. กรอก Size: `4`
3. เลือก Allocation method: `Indexed Allocation`
4. กดปุ่ม **Create file**
5. ชี้ให้เห็น Index Block และตัวเลขสรุปบน Summary Cards

**บทพูดผู้พรีเซนต์:**
> *"วิธีที่สามคือ **Indexed Allocation** เราสร้าง `database.db` ขนาด 4 บล็อก*
> *(ชี้ที่ Disk Grid)* *สังเกตว่าในวิธีนี้ มีบล็อกหนึ่งที่ถูกทำเครื่องหมายเป็น **Index Block** และอีก 4 บล็อกเป็น **Data Blocks** รวมแล้วต้องใช้พื้นที่ทั้งหมด $4 + 1 = 5$ บล็อก*
> *Index Block ทำหน้าที่เก็บ Pointer ชี้ไปยัง Data Block ทั้งหมด ทำให้เราทำ Direct Access ได้เร็ว โดยไม่ต้องเรียงบล็อกติดกันเหมือน Contiguous ครับ"*

### ช่วงที่ 3: จุดไฮไลต์ — ปรากฏการณ์ External Fragmentation (2:30 – 4:30)

> [!TIP]
> ส่วนนี้คือจุดสำคัญที่สุดของการนำเสนอ เพราะแสดงให้เห็นถึงความเข้าใจลึกซึ้งในเนื้อหาวิชา OS

**การกระทำบนหน้าจอ:**
1. กดปุ่ม **Reset simulation** (กด OK ยืนยัน)
2. สร้างไฟล์ Contiguous ขนาด 10 บล็อกติดกัน 5 ไฟล์:
   - `fileA` (ขนาด 10)
   - `fileB` (ขนาด 10)
   - `fileC` (ขนาด 10)
   - `fileD` (ขนาด 10)
   - `fileE` (ขนาด 10)
   *(ตอนนี้ดิสก์ถูกใช้ไป 50 บล็อก เหลือบล็อกว่าง 14 บล็อก)*
3. กดปุ่ม **Delete** ลบไฟล์ `fileB` (คืนบล็อก 10–19: ว่าง 10 บล็อก)
4. กดปุ่ม **Delete** ลบไฟล์ `fileD` (คืนบล็อก 30–39: ว่าง 10 บล็อก)
   *(ตอนนี้มี Free Blocks รวมกันถึง **34 บล็อก** แต่ช่องว่างที่ใหญ่ที่สุดมีขนาดเพียง 14 บล็อก)*
5. ในฟอร์ม: พยายามสร้าง `huge.zip` ขนาด **15 บล็อก** แบบ `Contiguous Allocation` -> กด **Create file**
   *(ระบบจะปฏิเสธและขึ้นข้อความสีแดงเตือน External Fragmentation)*
6. เปลี่ยน Allocation method เป็น `Linked Allocation` ด้วยขนาด **15 บล็อก** เท่าเดิม -> กด **Create file**
   *(ระบบสร้างไฟล์สำเร็จทันที!)*

**บทพูดผู้พรีเซนต์:**
> *(ช่วงกดสร้าง Error)*
> *"ตอนนี้ดิสก์ของเรามีบล็อกว่างกระจายอยู่รวมกันถึง 34 บล็อกครับ แต่เมื่อเราพยายามสร้างไฟล์ `huge.zip` ขนาด 15 บล็อกแบบ **Contiguous Allocation**...*
> *(กดปุ่ม)* *ระบบแจ้งว่าไม่สามารถสร้างได้! เพราะไม่มีช่องว่างที่เรียงติดกันยาวถึง 15 บล็อก นี่คือตัวอย่างที่ชัดเจนของปัญหา **External Fragmentation** ในวิชา OS ครับ*
>
> *(ช่วงเปลี่ยนเป็น Linked)*
> *แต่ถ้าเราเปลี่ยนวิธีจัดสรรเป็น **Linked Allocation** ด้วยขนาด 15 บล็อกเท่าเดิม...*
> *(กดปุ่ม)* *ระบบสามารถจัดสรรได้ทันที! เพราะ Linked Allocation สามารถนำบล็อกว่างที่กระจัดกระจายมาร้อยต่อกันได้ ทำให้ใช้พื้นที่ได้อย่างคุ้มค่าครับ"*

---

### ช่วงที่ 4: ความปลอดภัยและการคืนพื้นที่ (Invariants & Lifecycle) (4:30 – 5:30)

**การกระทำบนหน้าจอ:**
1. คลิกเลือกการ์ดไฟล์เพื่อแสดงการ **Highlight บล็อก**
2. กดปุ่ม **Delete** บนไฟล์ที่เหลือทีละไฟล์
3. แสดงตัวเลข Used / Free Blocks ที่ปรับเปลี่ยนแบบเรียลไทม์
4. พิมพ์ชื่อไฟล์ผิด เช่น ใส่ขนาดเป็น `-5` หรือชื่อว่าง เพื่อโชว์ **Input Validation & Atomic Check**
5. กดปุ่ม **Reset simulation** เพื่อคืนสภาพดิสก์เริ่มต้น

**บทพูดผู้พรีเซนต์:**
> *"นอกจากนี้ระบบของเรายังมีฟังก์ชัน Interactive เพื่อช่วยการเรียนรู้ เช่น การคลิกเพื่อ Highlight บล็อกของไฟล์นั้นๆ*
>
> *ในด้านความถูกต้อง (Correctness) เมื่อเราสั่งลบไฟล์ ระบบจะทำการคืนบล็อกทั้งหมดกลับเป็น Free Block พร้อมทั้งล้างพอยน์เตอร์และบทบาทของบล็อกอย่างสมบูรณ์ และมีระบบ Input Validation ป้องกันค่าติดลบหรือชื่อซ้ำ*
>
> *และที่สำคัญที่สุดคือ ไม่ว่าจะเกิดข้อผิดพลาดใดๆ สถานะของดิสก์จะไม่มีการเสียหายครึ่งๆ กลางๆ (Atomic Allocation) และผลรวมของ Used Blocks กับ Free Blocks จะรักษากฎความคงสภาพเท่ากับ 64 บล็อกอยู่ตลอดเวลาครับ"*

### ช่วงที่ 5: สรุปและเปิดรับคำถาม (5:30 – 6:30)

**บทพูดผู้พรีเซนต์:**
> *"โดยสรุปครับ โปรเจกต์ **FileAlloc** ช่วยแปลงคอนเซปต์ทฤษฎีเรื่อง File Allocation Methods ในหนังสือ ให้กลายเป็นภาพเคลื่อนไหวเชิงโต้ตอบที่เห็นได้ชัดเจน ทำให้เราเข้าใจการแลกเปลี่ยน (Trade-offs) ระหว่างความเร็วในการเข้าถึงข้อมูล ประสิทธิภาพการใช้พื้นที่ดิสก์ และ Overhead ของแต่ละวิธีได้อย่างถ่องแท้*
>
> *กลุ่มของพวกเราขอจบการนำเสนอเพียงเท่านี้ อาจารย์หรือเพื่อนๆ มีข้อสงสัยหรือคำถามเพิ่มเติมไหมครับ ขอบคุณครับ"*

## 3. คำถามที่พบบ่อยในการพรีเซนต์และแนวทางตอบ (Anticipated Q&A)

### Q1: ทำไม Indexed Allocation ถึงต้องใช้ขนาด $N + 1$ บล็อก?
> **แนวทางตอบ:** *"เพราะใน Indexed Allocation บล็อกข้อมูล $N$ บล็อกจะใช้เก็บเนื้อหาไฟล์จริงๆ ส่วนอีก 1 บล็อกพิเศษคือ Index Block ทำหน้าที่เป็นตารางเก็บ Pointer ชี้ไปยังบล็อกข้อมูลทั้ง $N$ ตัว เพื่อให้สามารถกระโดดเข้าถึงข้อมูลแบบ Direct Access ได้โดยตรงครับ"*

### Q2: ถ้า Contiguous Allocation เกิด External Fragmentation ในระบบปฏิบัติการจริงแก้ปัญหาอย่างไร?
> **แนวทางตอบ:** *"ในระบบปฏิบัติการจริงสามารถแก้ได้ด้วยการทำ **Defragmentation (Compaction)** คือการจัดระเบียบบล็อกที่ใช้งานอยู่ให้เลื่อนมารวมกัน เพื่อรวมพื้นที่ว่างให้กลายเป็นผืนใหญ่ หรือเปลี่ยนไปใช้ระบบไฟล์ที่รองรับ Extents หรือ Indexed/Inodes แบบระบบไฟล์สมัยใหม่ครับ"*

### Q3: ระบบนี้รองรับการบันทึกข้อมูลถาวร (Persistence) ไหม?
> **แนวทางตอบ:** *"ระบบนี้ออกแบบให้ทำงานเป็น In-memory Simulation บนเบราว์เซอร์ เพื่อให้เหมาะสำหรับการทดลองและเรียนรู้ในห้องเรียน เมื่อรีเฟรชหน้าเว็บหรือกด Reset ข้อมูลจะเริ่มต้นใหม่ ทำให้ผู้เรียนสามารถทดลองซ้ำได้โดยไม่มีข้อมูลตกค้างครับ"*

## 4. แผนสำรองกรณีเกิดปัญหา (Troubleshooting & Contingency Plan)

- **กรณีเผลอกดผิดหรือลำดับรวน**: ให้กดปุ่ม **Reset simulation** ด้านบนขวา แล้วกดยืนยัน ระบบจะกลับสู่สถานะว่าง 64 บล็อกทันทีภายใน 1 วินาที
- **กรณีมองเห็นสีไม่ชัดเจน**: สามารถคลิกที่การ์ดไฟล์ด้านล่าง เพื่อให้ระบบเปิดโหมด **Highlight** เฉพาะบล็อกของไฟล์นั้นขึ้นมาอย่างเด่นชัด
- **กรณีเมาส์ใช้งานไม่สะดวก**: ตารางบล็อกและปุ่มทั้งหมดรองรับการใช้งานผ่านคีย์บอร์ด (Tab และ Enter / Spacebar) ตามมาตรฐาน Accessibility
